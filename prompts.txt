# Plan: a streaming CSV payments engine (a library plus a small CLI)

This plan comes from a short multi-agent design run. Three planners drafted independently: one focused on maintainability, one on performance, one on correctness. A judge and a separate spec auditor reviewed the drafts, and the merged plan is built mainly on the correctness draft. I checked three crate-API claims against the crate sources on your machine and all three hold: csv `1.4.0`'s `Trim::All` allocates a new record on every row, `rust_decimal` `1.43.0`'s parser accepts `1_000`, and its addition silently rounds instead of reporting an overflow. `payments-engine-old/` was not used.

## Guiding principles
- **Correct first, then clean, then fast.** The spec ranks clean code above efficient code. Every performance choice here either costs nothing in readability, or sits behind a module boundary so it can be swapped later.
- **Parse, don't validate.** CSV text becomes typed values (`Amount`, `ClientId`, `TxId`, `Transaction`) at a single boundary. The engine never sees strings, serde or csv.
- **One place per rule.** Balance arithmetic lives in `Account::apply_delta`, the dispute lifecycle in `DisputeState::next`, and the lock rule in `ensure_unlocked`.
- **Never half-apply, never half-print.** A rejected transaction changes nothing. A fatal error produces empty stdout and a non-zero exit code.

## Key design decisions

| Area | Choice | Why |
|---|---|---|
| Money type | `Amount(rust_decimal::Decimal)`: more than 0, at most 1e15, at most 4 decimal places | Exact and well known to reviewers. The 1e15 cap keeps every balance below the point where `Decimal` addition starts rounding silently. An i64 fixed-point type is left as future work: it saves no memory here and needs a hand-written parser and formatter. |
| Parsing amounts | Read the amount as text, allow only digits and one `.`, then convert with `from_str_exact`. Reject more than 4 decimal places instead of rounding. Never use `Decimal`'s own serde. | `Decimal`'s serde goes through the f64 path in csv and loses digits. The plain parsers accept `1e3` and `1_000`. Rounding money would create or destroy it. |
| Reading the CSV | Trim only the header, `flexible(true)`, one reused `StringRecord`, rows that borrow `&str`, and fields trimmed by our code | No heap allocation per row once running. Accepts rows like `dispute, 1, 1` with no amount column. Columns are matched by header name, and every error keeps its line number. |
| Transaction type | `struct Transaction { client, tx, kind }`, where `kind` is Deposit(Amount), Withdrawal(Amount), Dispute, Resolve or Chargeback | Only deposits and withdrawals carry an amount, so a dispute row can't hold one. |
| Stored transactions | `HashMap<TxId, DepositRecord>` holding **accepted deposits only**. Each record is 20 bytes, checked by a compile-time assert. | Only deposits can be disputed, so memory grows with deposits, not with all rows. |
| Accounts | `BTreeMap<ClientId, Account>` | Output comes out sorted for free and accounts are created only as clients appear. |
| Dispute lifecycle | `Undisputed → Disputed → (Resolve → Undisputed \| Chargeback → ChargedBack, which is final)`, one exhaustive `next()` with no catch-all arm | The 9 combinations get a 9-case test, and adding a state forces every match to be updated. |
| Errors | `thiserror` enums: `TxError` (rejected by business rules, row skipped), `RowError` (malformed row, skipped), `RunError` (fatal). Exit codes: 0 on success, 1 on runtime error, 2 on usage error. | Matches the spec's "ignore, partner error" rule. Real I/O problems stop the run before any output. |
| Safety | `unsafe_code = "forbid"`; clippy `unwrap_used`, `expect_used` and `panic` made fatal in CI; checked arithmetic; `overflow-checks = true` in release builds | Hostile input can't cause a panic. |
| Concurrency | Single-threaded, with `run<R: Read, W: Write>`. Sharding by client is described in the README but not built. | Sharding by client is valid because a dispute must match its deposit's client. |

## Performance and memory
- Each row reuses one buffer and does one account lookup and at most one deposit-map operation, with no heap allocation per row. Throughput is limited by parsing.
- Accounts use at most about 3–5 MB, since client ids are u16.
- Deposits cost about **29–57 bytes per accepted deposit**: about 52 MB for 1M deposits and about 3.4 GB for 100M. The theoretical worst case of 2³² deposits is about 215 GB, which doesn't fit in RAM. The README says so and lists the ways to bound it.

## Edge-case decisions that matter most
The full 42-row assumptions table is in the plan file.
- Only deposits can be disputed. A dispute whose client differs from the deposit's client is ignored.
- A dispute after the funds were withdrawn is allowed and makes available negative. This is the fraud scenario the spec describes.
- A locked account rejects deposits and withdrawals, but disputes, resolves and chargebacks are still processed.
- A duplicate deposit id is rejected and the original record is kept. Dispute, resolve and chargeback rows never create an account.
